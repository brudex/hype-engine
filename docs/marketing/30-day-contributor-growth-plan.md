# Hype Engine 30-day contributor growth plan

## Objective

Build a repeatable contributor funnel for Hype Engine: discovery, evaluation,
first contribution, retention, and public recognition.

The first-month targets are:

- 50–100 GitHub stars
- 10 successful Docker evaluations
- 5 useful issues or discussions from users
- 3 first-time contributors
- 2 merged external pull requests
- 1 returning contributor

## Automation rules

The daily job completes the first unchecked day below and records evidence in
`docs/marketing/traction-log.md`.

It may autonomously:

- Research public information and inspect repository state.
- Draft content, issues, documentation, and repository changes.
- Run tests and commit repository-only changes when the day's task requires it.
- Review public metrics and organize findings.

It must stop and alert the project owner before:

- Publishing posts, releases, issues, discussions, or comments.
- Messaging or emailing potential contributors.
- Changing GitHub repository settings, topics, labels, or permissions.
- Creating external community accounts or events.
- Spending money or starting paid promotion.
- Using credentials or accepting license/legal terms.

If blocked, the job leaves the day unchecked, documents the blocker, and asks
for the exact permission or input needed. It must not silently skip to the next
day.

## Week 1 — Build the contributor funnel

- [x] **Day 1 — Baseline audit.** Record current stars, forks, watchers, open
  issues, pull requests, release state, topics, Discussions status, README
  conversion gaps, and onboarding friction. Create `traction-log.md`.
- [x] **Day 2 — Repository positioning.** Draft the improved GitHub
  description, homepage setting, topic list, and concise positioning statement.
  Apply repository-file improvements; request approval for GitHub settings.
- [x] **Day 3 — Contributor backlog.** Identify and write ten scoped,
  valuable contribution opportunities covering frontend, backend, providers,
  testing, documentation, accessibility, and Docker.
- [x] **Day 4 — Issue quality.** Add or improve issue templates, label
  taxonomy, issue-writing standards, and a contributor issue checklist.
- [x] **Day 5 — Contributor-ready issues.** Prepare the first five `good first
  issue` and three `help wanted` issue drafts with context, suggested files,
  acceptance criteria, and verification steps. Request approval before
  publishing them.
- [x] **Day 6 — README conversion.** Improve the README hero, badges,
  positioning, feature presentation, live demo call-to-action, and contributor
  invitation while preserving the current 78-second tour.
- [x] **Day 7 — Release package.** Prepare `v0.1.0` release notes, known
  limitations, upgrade/install notes, screenshots, and contributor call.
  Request approval before creating or publishing the GitHub release.

## Week 2 — Create the launch story and recruit carefully

- [x] **Day 8 — Founder story.** Draft “Why I open-sourced Hype Engine,”
  including the problem, why existing tools were insufficient, and the project
  vision.
- [x] **Day 9 — Social launch kit.** Draft tailored LinkedIn, X, DEV/Hashnode,
  and short community announcements with one clear action per post.
- [x] **Day 10 — Community home.** Recommend GitHub Discussions or Discord
  based on current traction, define categories/channels and response standards,
  and request approval before enabling or creating anything.
- [x] **Day 11 — Contributor prospecting.** Build a private research list of
  20 relevant developers and communities based only on public open-source work.
  Do not contact anyone.
- [x] **Day 12 — Personal outreach drafts.** Write ten individualized,
  non-spam invitation drafts tied to specific contribution issues. Request
  approval before sending any message.
- [x] **Day 13 — Soft launch.** Prepare the approved founder story and social
  posts for publication, verify every link and asset, then request final
  approval before publishing.
- [x] **Day 14 — Response and triage.** Review public responses, issues, and
  questions; draft helpful replies; identify friction and update the FAQ or
  documentation. Request approval before posting replies externally.

## Week 3 — Demonstrate differentiation

- [ ] **Day 15 — First-user evidence.** Prepare a structured user interview or
  feedback request and a case-study template. Ask the owner for candidate users
  or permission to invite demo users.
- [ ] **Day 16 — Comparison content.** Draft a fair, verifiable Hype Engine
  comparison with Mixpost, Buffer, and other relevant self-hosted options.
  Clearly distinguish facts, limitations, and roadmap items.
- [ ] **Day 17 — Technical story.** Draft an architecture article covering
  Express, PostgreSQL, Sequelize, workers, provider integrations, and Social
  Flows, with contribution entry points.
- [ ] **Day 18 — Show HN package.** Draft the title, submission text, founder
  comment, FAQ responses, and launch readiness checklist. Do not submit.
- [ ] **Day 19 — Community-specific posts.** Draft distinct, rule-compliant
  posts for relevant self-hosted, open-source, JavaScript, and developer
  communities. Verify community rules and request approval before posting.
- [ ] **Day 20 — Coordinated launch.** Recheck CI, demo health, onboarding,
  issues, release notes, and media. Present the exact launch sequence and
  request approval for each external publication.
- [ ] **Day 21 — Funnel review.** Measure visits where available, stars,
  forks, demo usage signals, issues, discussions, contributors, and conversion
  blockers. Recommend the next week's adjustments.

## Week 4 — Retain contributors and compound traction

- [ ] **Day 22 — Onboarding improvements.** Use feedback and observed
  questions to shorten setup time, improve development seed data, and clarify
  the architecture and testing workflow.
- [ ] **Day 23 — Office hours.** Prepare the agenda, announcement, contributor
  questions, and follow-up template for a first community office hour. Ask the
  owner to select a platform and time before scheduling.
- [ ] **Day 24 — Contributor recognition.** Prepare a repeatable first-PR
  welcome, release-note acknowledgement, contributor spotlight, and reviewer
  response-time policy.
- [ ] **Day 25 — High-value contribution spec.** Turn the most requested
  provider or workflow improvement into a detailed `help wanted` specification
  that an external contributor can own.
- [ ] **Day 26 — Second content wave.** Draft a progress update showing shipped
  improvements, community feedback, contributor wins, and the next open issues.
- [ ] **Day 27 — Ecosystem partnerships.** Identify ten relevant newsletters,
  directories, podcasts, maintainers, or self-hosted communities and draft
  individualized pitches. Do not contact them without approval.
- [ ] **Day 28 — Public roadmap.** Draft a 90-day roadmap and community poll
  based on evidence collected during the month. Request approval before
  publishing.
- [ ] **Day 29 — Retrospective.** Compare results with the baseline and targets,
  identify successful channels, calculate contributor conversion, and stop
  low-value activities.
- [ ] **Day 30 — Traction report and next cycle.** Produce a public-safe
  30-day report, recognize contributors, recommend the next 30-day plan, and
  request approval before publishing the report or scheduling another cycle.

## Daily traction log format

Each entry in `docs/marketing/traction-log.md` must include:

- Date and plan day
- Work completed
- Files or external drafts produced
- Verification performed
- Current metrics, when relevant
- Decisions made
- Blockers
- Exact owner input or permission required
- Recommended next action
